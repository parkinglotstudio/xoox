## A. 맵 / 지형 파이프라인

### A-1. 공간 모델 (확정)

한 섬 ≈ **1 km**, **3×3 = 9칸**, 칸 ≈ **333 m**. 보행은 육지 십자 5칸만.

```
i00 미니맵   i01 북부 큰숲   i02 미니맵
i10 서부     i11 중앙         i12 동부
i20 미니맵   i21 들판·스폰    i22 미니맵
```

- 코너 4칸(`i00/i02/i20/i22`)은 **바다 구멍이 아님**. 미니맵용 육지(숲/산). 보행만 불가.
- 스폰 = `area_i21` (`is_spawn=TRUE`). 현재 컨셉은 **부두가 아니라 남쪽 들판**.
- 문서 상수: `data/ui/layout/journey_tiles.json` (`walkable`, `sea_corners_art_only`). **`src/`는 이 JSON을 읽지 않음** — 코드 쪽은 `LAND_SECTOR_IDS`에 같은 집합을 하드코딩.

### A-2. 저작 형식 (무엇이 “원본”인가)

| 형식 | 역할 | 본편 런타임이 읽는가 |

| 섹터 컨셉 PNG 2048² | 미니맵·에디터·3D 바닥 스플랫 입력 | **예** (`sector_scale.json` URL) |
| `sector_scale.json` | 미터·안개·섹터별 after/before 경로 | **예** |
| `journey3d_layout.json` | 3D 렌더 스케일·카메라·안개 | **예** |
| CSV (`area_*`) | 구역 그래프·노드·존·프롭 | **예** (`src/data.ts`) |

| `tileset/` 디테일 스탬프 | README에 **예정** | 디렉터리 없음 |

마스크 스키마 (`src/mapMaskTool/types.ts`):

```text
MaskDoc = { version, sector_id, size, note, layers: Partial<Record<LayerId, dataURL PNG>> }
LAYER_IDS = land, walk, path, forest, flower, pond, lake, rock,
            debris, blight, farm, village, dock, node, poi
```

- `walk` = “갈 수 있는 땅 전부”가 아님. **인게임 타일 작업 구역**(십자). `walk` 밖 ∩ `land` 안 = 미니맵만.
- Phase 0→4: 레이아웃 → 외곽(림) → 작업구역 → 소프트 액센트 → 미리보기. `MASK_PHASES`.
- `farm` / `village` / `dock`는 레이어 정의에 있으나 **enabled: false** (거주 아트 보류).

**핵심 갭:** 마스크는 툴·파이프라인 SSoT이지만, **본편 3D 바닥은 마스크 레이어를 직접 스탬프하지 않는다.** 컨셉 PNG를 분석해 타일을 섞는다.

### A-6. 런타임 로드 경로

```
src/main.ts init()
  → loadGameData()          // src/data.ts — 위 CSV
  → initExplore()           // 탑뷰 미니맵 (로비에서도 가능)
  → enterJourney()
      → initJourney3D()     // 외출 때 WebGL. 로비에서는 IslandTerrain 없음
          Journey3DView.enter(areaId)
            → loadJourney3DConfig()
            → IslandTerrain (스폰 칸 우선, 이웃 BFS)
            → scatterForArea()  // area_prop_config만
            → refreshNodes()    // area_npc_config
```

| 층 | 모듈 | 로드하는 것 |
|---|---|---|
| 탑뷰 | `src/explore.ts` `ExploreView` | `area_config` 배경, 연결, NPC. `sector_scale.json`으로 액터·안개 |
| 3D 글루 | `src/stage/world3d/Journey3DView.ts` | 바닥 + CSV 프롭 + 노드 + 정화 루프 |
| 3D 무대 | `JourneyStage3D.ts` | 카메라, 빌보드, 해안 InstancedMesh, 원경 원통 |
| 바닥 | `IslandTerrain.ts` | 물 플레인 + 육지 5칸 메시 |
| 스플랫 | `islandFloorSplat.ts` | 컨셉 PNG → 타일 캔버스 (`SRC=768`, `OUT=2048`) |
| 스트리밍 | `islandLoadOrder.ts` | `LAND_SECTOR_IDS`, `landLoadOrder()` i21→i11→나머지 |
| 좌표 SSoT | `islandMapShared.ts` | 스케일 URL, 컨셉 URL, 마스크 URL (마스크 URL은 툴용) |

`IslandTerrain.paintLand()` 요약:

1. `conceptUrlFor(..., purified=true)` → **`sector_*_after.png`만**.
2. `paintSectorFloorFromImage()` / `analyzeConceptMesh()` — 바다 flood-fill, 지붕/오브젝트 인페인트, 타일 스탬프.
3. 알파 = 바다 마스크. 오염 = 셰이더 틴트 (`POLLUTED_TINT`), before PNG 스왑 아님.
4. `stickerDrafts`를 컨셉 blob에서 뽑지만 **본편 `scatterForArea`는 쓰지 않음**.

레거시: `JourneyStage3D`의 옛 `floor`/`detail` 메시는 `island.ready` 후 `visible=false`. 주석: 타일 섬이 올라오면 디테일 오버레이를 끈다.

좌표 동기: 3D가 이동을 소유 → `onMove` → `explore.syncFrom3D(xPct, yPct, yawDeg)`. 칸 이동: `explore.onAreaChange` → `journey3d.enter`.

## B. 오브젝트 / 프롭 표현

### B-1. 런타임 표현 (있는 것 / 없는 것)

| 기법 | 사용처 | 비고 |
|---|---|---|
| **세로 빌보드 `THREE.Mesh` + 공유 `PlaneGeometry(1,1)`** | 일반 프롭 | 둠식 세움판. 기본 `billboard=true` (카메라 yaw) |
| **PNG 스티커** | `data/art/props/sticker/` | `WorldProp.art` → `/art/props/sticker/{file}` |
| **절차 캔버스 폴백** | `propArt.ts` | `art` 없으면 `PropKind`별 `CanvasTexture` |
| **텍스처/머티리얼 공유** | `stickerArtTexture` / `stickerArtMaterial` | 같은 PNG = 1장. 최대 512px, 알파 펀치 |
| **`THREE.InstancedMesh`** | `group_id === "sea_wall"`만 | 아트 URL별로 배치. 거리 스트리밍 |
| **`THREE.Sprite`** | `WorldNode` (NPC 마커) | 프롭 CSV와 분리 |
| **바닥 스플랫 메시** | `IslandTerrain` | 타일 캔버스. 프롭 아님 |
| **컨셉 blob → 스티커 초안** | `backgroundProps()` | 구현됨, **본편 enter에 미연결** |
| **시드 난수 스캐터** | `scatter.ts` `scatterProps()` | CSV가 있으면 우선. **importer 없음** |
| GLTF / `.glb` / 병합 지오메트리 / 텍스처 아틀라스 / 프롭 LOD | — | **없음** |

타입 (`src/stage/world3d/types.ts`):

```text
PropKind = building | tower | fence | sign | crate | barrel | pole | tree | bush | debris
WorldProp = id, xPct, yPct, kind, hM?, aspect?, art?, billboard?, yawDeg?,
            tint?, collide?, collideR?, purifyTarget?, lifeBlightId?, groupId?
```

`PROP_DEFAULTS` (`propArt.ts`): 전 kind `billboard: true`. 예: tree 6.4 m, building 12.5 m, bush 1.35 m.

스티커 로스터 (`data/art/props/sticker/roster.json`):

- `nature_active`: tree_04~07, grass_01~03, flower_01~03 — 노트는 “CSV에 연결됨”
- `nature_draft`: tree_01~03 — “파일 보관, CSV 미사용”
- houses 4종, 일반 props (tower/fence/sign/crate/barrel/pole/lantern/debris/life_mecha_dog)

**실제 커밋된 `area_prop_config.csv`:** 361행, **전부 `sea_wall`**, art는 `prop_sticker_tree_06.png` / `tree_07.png`. 구역: `area_i21` 82, `i10`/`i01`/`i12` 각 93. **`area_i11` 0행.** 들판 나무(tree_04/05)·풀·꽃·집은 라이브 CSV에 없음.

스티커 PNG는 체크아웃에 **존재함** (`prop_sticker_tree_01`~`07`, grass, flower, houses, …).

### B-2. 배치 데이터 포맷

**SSoT 헤더** (`data/area_prop_config.csv` = `AreaPropDef` in `src/types.ts`):

```text
prop_id, area_id, kind, x_pct, y_pct, yaw_deg, h_m,
group_id, collide, purify_target, life_blight_id, art, note
```

| 필드 | 의미 |
|---|---|
| `x_pct`, `y_pct` | 섹터 맵 0–100. y=0 북(아트 위) = 3D −Z |
| `yaw_deg` | 고정 평면일 때. 빌보드는 카메라가 덮음 |
| `h_m` | 높이(m). 폭 = `hM * aspect` (`stickerTrees.aspectForPropArt`) |
| `group_id` | 특수: **`sea_wall`** = 해안 방벽 인스턴싱 + 개별 메시 스트림에서 제외 |
| `collide` | 원반 장애물. 기본 반경 `COLLIDE_R` (tree 1.35, building 2.6, …) |
| `collideR` | CSV에 컬럼 없음. `propFromCsv`가 sea_wall에 tree_07=2.6 / 그 외=2.05를 넣음 |

코드가 이미 적은 성능 메모:

### C-2. 좌표계 · 카메라

**% 좌표 (2D ↔ 3D 공유)**  
`x_pct`/`y_pct` 0–100. y=0 북 = 3D −Z. yaw 0° = 북(−Z).

**미터 — 두 스케일**

| 이름 | 값 | 의미 |
|---|---|---|
| `sector_world_*_m` / `SECTOR_M` | **333** | 설계 “실제” 칸. 멀티섹터 절대 원점 |
| `island_world_m` | 1000 | 섬 한 변 |
| `world_m` (레이아웃 JSON) | **110** (코드 기본 70) | **한 칸을 몇 m로 그릴지.** %는 그대로라 미니맵은 안 깨짐 |
| `character_height_m` (스케일 JSON) | 1 | 2D 에디터 비유 |
| `char_height_m` (3D JSON) | **1.95** | 3D 방랑자·원경 배수. GDD 46: 두 숫자를 섞지 말 것 |
| `centerOnFocus` | true | 활성 칸을 원점으로 당겨 그림 |

`areaToWorld` / `sectorOrigin`: 그리드 칸 원점. 포커스 모드에서는 로컬 xz ≈ 플레이어 월드.

**카메라** (`journey3dConfig.ts`, GDD 46):

- `PerspectiveCamera`, FOV **72**, 기본 **`view_mode: "tps"`** (등 뒤, 플레이어 스프라이트 보임).
- TPS: `tps_distance_mul=3.2` · `tps_height_mul=1.9` → 거리 ≈ 6.2 m, 높이 ≈ 3.7 m. lookAt ≈ 수평.
- `"fps"`: 플레이어 스프라이트 숨김. `fpv-tool` / `setViewMode`.
- 원경: 원통 한 장, 반지름 ≈ fog.far×0.86, 높이 `charH*18`, xz는 카메라를 따라감.

탐방 안개(탑뷰) `fog_vision_m=10` (GDD 45)와 3D fog `30`은 **다른 노브**.

배치 함의: 카메라는 거의 수평이라 **근경 빌보드(나무·풀)가 “옆 풍경”**이고, 먼 산은 원통. 탑뷰 섹터 PNG에 산을 구워 넣지 않는다. 밀도·높이는 TPS 발밑(world_m 110 ≈ 3.4 m/섹터%)에 맞춰야 한다. 333 m 설계 밀도를 그대로 심으면 발밑에 과밀·원경에 공허해진다.

### D-3. 설계 의도 (배치 논의용으로 압축)

1. **공간 = RPG.** 콘텐츠는 날짜가 아니라 칸·노드에 붙는다. 왕복이 가능해야 한다.
2. **한 통짜 섬.** 칸마다 다른 섬 모양 금지. 코너는 바다로 비우지 않음.
3. **바닥과 소품은 나중 레이어.** 마스크로 구역을 읽히게 한 뒤, 타일+빌보드로 채운다. 복셀/박스 높이는 후순위(해안만 타협 후보).
4. **거주는 선반.** 집·부두·마을 아트는 마스크에서 꺼 두었고, 해당 프롭은 `i21_props_shelved.csv`.
5. **근경은 스티커, 원경은 원통.** 섹터 PNG에 산을 넣지 않음.
6. **들판 손맛**은 다섯 자리 + 해안 나무/들풀 그래픽. 라이브 월드는 아직 해안 `sea_wall` 나무 띠가 그 의도에 가장 가깝다.
7. **반복 소품은 싸게.** 해안 밀도에서 이미 InstancedMesh+스트림을 넣었다. 내륙 RPG 밀도는 같은 패턴의 일반화가 자연스러운 다음 기술 질문이다.

3. **렌더 미터 ≠ 설계 미터.** 333 m 설계 간격으로 심고 110 m로 그리면 발밑이 과밀. 배치 툴/CSV에 “어느 스케일 기준인가”가 없음.
4. **충돌이 전부 원반.** 울타리 줄·바위 군집·좁은 숲길은 원을 겹치면 길이 막히거나 통과한다. `path` 마스크는 보행 메시가 아님.
5. **마스크와 3D가 한 소스가 아님.** 숲 마스크를 바꿔도 나무는 안 움직임. 더블 소스(페인트 vs CSV).
6. **카메라가 수평 TPS.** 낮은 풀은 발밑에만 보이고, 키 큰 해안 나무는 실루엣이 됨. 종류·높이 믹스가 필요.
7. **상호작용 슬롯이 얇음.** 줍기=노드, 잔여칠=`purify_target`, 생명뭉치=미배선. “조사할 바위/상자”를 프롭으로 늘리면 훅을 더 열어야 함.
8. **i11 허브가 비어 있음.** 중앙을 지날 때 해안 띠도 없음.

### F-1. 스케일 진리표 — “1 km”가 가리키는 것

두 자(尺)가 동시에 살아 있다. 섞이면 밀도 계산이 9배 틀린다.

| 자 | 출처 | 칸 한 변 | 3×3 섬 한 변 | 쓰는 곳 |
|---|---|---:|---:|---|
| **설계(내러티브·미니맵)** | `sector_scale.json` `island_world_m=1000`, `sector_world_*_m=333` | **333 m** | **999 m ≈ 1 km** | GDD 42, 탑뷰 `ExploreView`, 마스크 마스터 |
| **3D 렌더(발밑)** | `journey3d_layout.json` `world_m=110` → `IslandTerrain.cellSize = worldM` | **110 m** | 한 화면에 연속으로 안 펼침 | `JourneyStage3D`, 프롭 %, 충돌 |

**“1 km”의 뜻 (코드와 문서가 일치하는 부분)**  
`3 × 333 m = 999 m`. 섬 **설계 바운딩 스퀘어**다. `island_overview_1km.png` · GDD 42 「섬 ≈ 1 km」와 같다. 3×3 **격자 전체**의 한 변이지, 플레이어가 한 번에 걷는 연속 메쉬의 한 변이 아니다.

**걷히는 범위 (설계 자)**

| 범위 | 식 | 값 |
|---|---|---|
| 보행 칸 | 십자 5 (`i01,i10,i11,i12,i21`) | 코너 4는 미니맵만 |
| 칸 면적 | 333² | ≈ 1.11×10⁵ m² /칸 |
| 보행 5칸 면적 | 5 × 333² | ≈ **5.54×10⁵ m²** |
| 남북(또는 동서) 최장 보행 | 3칸 직선 `i21→i11→i01` | **≈ 999 m (설계)** |
| `island_usable_land_m=700` | 스케일 JSON | **선형 “감”** (코너 제외). 렌더 한 변이 아님 |

**3D에서 실제로 펼쳐지는 범위**

본편은 `centerOnFocus: true`. 활성 칸이 원점, 플레이어는 `±(worldM/2 − 2)` ≈ **±53 m** 안에 갇힌다. 가장자리에서 `onCellEdge` → 이웃 `enter` → 그룹을 다시 원점으로. **3D 월드를 1 km로 이어 붙이지 않는다.**

이웃 육지 메시는 `cellSize=110` 간격으로 옆에 놓인다. 안개 너머는 `cullLandByView(keepM ≈ fog.far+12)`로 끈다. 주석: 「5장 2048 투명 쿼드가 동시에 채워지면 GPU가 같이 돈다.」

| 3D에서 한 시점 | 대략 |
|---|---|
| 지금 걷는 칸 | **110 × 110 m** |
| 시야(3D fog far) | `30 × fog_far_mul(1)` = **30 m** (정화 시 ×1.25까지) |
| 프롭 생성 반경 | `propStreamM = fog.far × 1.12` ≈ **34 m** (디스폰 1.25× ≈ 42 m) |
| 원경 원통 반지름 | `max(18, fog.far × 0.82)` ≈ **25 m** (코드. GDD 46의 0.86·charH×18과 **어긋남**) |
| 세 칸을 다 건너 걸은 3D 거리 | 3 × 110 = **330 m** (설계 999 m의 축소 보행) |

**밀도와의 관계**  
CSV는 **%** 라 칸을 110으로 그리든 333으로 그리든 같은 행이 칸을 채운다. 같은 82그루가 110 m 칸에 있으면 333 m 칸보다 **면적 밀도 ≈ 9배**. 지금 라이브 해안 나무는 “1 km 섬에 361그루”가 아니라 **110 m 칸 둘레에 칸당 ~80그루**다.

| 현재 라이브 (렌더 110 m 기준) | 값 |
|---|---|
| i21 | 82그루 / 12 100 m² ≈ **0.0068 / m²** (둘레 띠. 면적 균일 아님) |
| i10 / i01 / i12 | 각 93 |
| i11 | **0** |
| 둘레 간격 (한 변 110 m × 4, 82그루) | ≈ **5 m당 1그루** 차수 |
| 스트림 원 π·34² | ≈ **3 630 m²** — 해안을 따라 걸을 때만 그 원 안에 나무가 몰림 |

균일 내륙을 같은 스트림 원에 깔면: 원 안 개수 ≈ 밀도 × 3 630. 예: 0.01/m² → ~36, 0.04/m² → ~145, 0.1/m² → ~360. (차수. 기기는 미실측.)

**불확실:** 탑뷰 안개 10 m와 3D 안개 30 m를 같은 “시야”로 읽으면 안 된다. 유저가 말하는 1 km가 **미니맵 섬**인지 **외출해서 걸은 거리**인지는 이 표만으로 확정하지 않는다. 코드가 보장하는 건 “설계 격자 한 변 ≈ 1 km, 3D 칸 = 110 m”뿐이다.

### F-2. 바닥 (terrain) 비용

**만드는 법 (프레임이 아니라 칸 로드 시 1회)**  
1. 컨셉 `sector_*_after.png` **2048² RGB** (~3–4 MB 파일).  
2. `islandFloorSplat`: 768²로 분석 → 바다 flood-fill · 오브젝트 인페인트 24패스 · 타일 5종(풀/숲/흙/판석/물, 소스 512²)을 2048²에 스탬프 (`REPEAT=24`).  
3. GPU: **색 2048² CanvasTexture + 밉맵**, **알파 마스크 1024²**. 메시는 `PlaneGeometry(1,1)` 한 장, 스케일 = `cellM`.  
4. `MeshBasicMaterial` + `wirePolluteShader` (정화 원·파도 유니폼, 최대 8 foci). 정화 후 5칸을 다시 스플랫하지 않음.  
5. 물: 타일 1장 반복 `repeat(20,20)`, 플레인 한 장, 폭 `cellM × 4` ≈ 440 m.  
6. 레거시 `floor`/`detail` 쿼드는 `island.ready` 후 `visible=false`.

**프레임 비용 드라이버**

| 항목 | 규모 | 비고 |
|---|---|---|
| 육지 draw | 포커스 1 + 컬에 걸린 이웃 0–2 | 지오메트리 4버텍스. **필레이트 = 110 m 쿼드 × 투명(alphaTest 0.12)** |
| 색 텍스처 VRAM | 2048² RGBA + 밉 ≈ **~21 MB/칸** 차수 | 주석이 이미 「들판에서 VRAM이 먼저 나간다」 |
| 마스크 VRAM | 1024² 차수 **~4 MB/칸** | |
| 동시에 메시가 있는 칸 | 스폰 우선 + 이웃 `preloadNeighbors` | 최대 육지 5. 그리기는 컬 |
| CPU 스플랫 | 768² 인페인트 + 2048² 스탬프 | **히치.** 프레임 루프 아님 |
| 소스 타일 5종 | 512², 공유 캐시 | 스플랫 입력이고 매 프레임 바인드 다수는 아님 |

**헤드룸 (바닥을 유지한 채 프롭을 늘릴 수 있는가)**  
바닥은 **칸당 쿼드 1 + 큰 텍스처**이지, 프롭 개수에 비례하지 않는다. 프롭을 늘려도 스플랫 해상도·draw 수는 그대로다. 같이 쓰는 자원은 **VRAM·필레이트**다. 코드가 5×2048을 동시에 켜지 말라고 이미 적었다. 프롭 텍스처(아래)와 **합산 VRAM**이 한계면 바닥이 먼저 자리를 차지한 상태다. 구조상 바닥이 “프롭 밀도 상한”을 숫자로 조이지는 않는다.

**불확실:** GPU에서 2048 캔버스가 실제로 RGBA8인지, 마스크 밉 생성 여부, 모바일에서 5칸 상주 시 실제 MB. 프로파일 없음.

### F-3. 하늘 / 원경 비용

| 리소스 | 파일 | GPU에 올라가는 해상도 |
|---|---|---|
| `horizon_mountains_{polluted,purified}.png` | 4096×2048 RGB, 4.9 / 8.9 MB | 원통 1개 (`CylinderGeometry` 48세그, `fog: false`, BackSide) |
| `sky_{polluted,purified}.png` | 4096×2048 RGB. polluted 파일은 **33 KB**(거의 단색), purified 5.1 MB | `scene.background` Equirect. 디스크 크기 ≠ VRAM |
| 원통 위치 | 매 프레임 카메라 xz를 따라감 | 높이 `max(20, charH×22)` ≈ 43 m (코드. GDD 46과 불일치) |

VRAM 차수: 4096×2048을 RGBA8+밉으로 올리면 **장당 ~30–45 MB**. 정화전/후 하늘·원경을 `loadSkyArt`가 **둘 다 미리** 받는다 → 상한 차수 **~0.1–0.2 GB** (업로드 포맷·equirect 변환 여부에 좌우). 지오메트리는 삼각형 ~96. draw **원통 1**.

**프롭 대비:** 하늘/원경은 **고정비**. 나무 개수와 무관. 필레이트도 원통 한 겹. **하늘이 내륙 밀도 상한을 조이지 않는다.** 다만 이미 큰 텍스처라, 기기 VRAM이 빠듯하면 프롭 512 스티커와 **같은 예산**을 나눠 쓴다.

**불확실:** Three 0.185가 equirect background를 풀 해상도 큐브맵으로 변환하는지(변환 시 VRAM 더 큼). 실측 없음.

### F-4. 프롭 배치 아키텍처 용량

**지금 경로 (칸 enter 시)**  
`area_prop_config` → 그 `area_id`만 `setProps`. **이웃 칸 나무는 안 보인다** (바닥 메시만 이웃).  
`sea_wall` → 아트별 `InstancedMesh` 1개, `count` = 스트림 원 안. 장마다 `instanceMatrix` 갱신(카메라 빌보드).  
그 외 → 34 m 안만 `THREE.Mesh`. 공유 `PlaneGeometry`, `art` 있으면 머티리얼/텍스처 캐시. 스티커는 긴 변 **최대 512**로 다운스케일.

**CSV vs 그리는 것**

| | 라이브 데이터 | 구조가 허용하는 것 |
|---|---|---|
| 행 수 | 361 (해안만) | 텍스트 CSV. **수천 행 자체는 부하가 아님** |
| 종류 | tree 2 PNG | `PropKind` 10 + 임의 `art` URL |
| 인스턴싱 | `group_id==="sea_wall"`만 | 같은 패턴을 다른 그룹에 쓸 **코드는 해안에만 있음** |
| 충돌 | 카탈로그 **전부** 원반, 매 WASD `O(n)` 4회 | 스트림과 무관. 칸 전체 n |

**내륙 CSV를 늘릴 때 먼저 깨질 후보 (구조 순서)**

1. **Draw call + 알파 오버드로우** — `sea_wall`이 아닌 나무는 Mesh 1 = draw ≈ 1. 스트림 원 안 100–300 세움판(DoubleSide, alphaTest 0.1)은 모바일 필레이트에 먼저 닿을 수 있음. InstancedMesh면 draw는 **아트 종류 수**로 남음.  
2. **고유 텍스처 수** — 바인드/VRAM. 같은 나무 500그루/1 PNG는 캐시 1장(~1 MB 차수 @512). PNG 30종이면 차수 수십 MB + 셰이더 스위치. **아틀라스 없음.**  
3. **충돌 원반** — `resolveCircleMove`가 카탈로그 전부. n=10² 차수는 여유, n=10⁴/칸이면 WASD마다 수만 `hypot`. A*(`guard 4000`, 그리드 2.2 m, 칸의 절반)는 n이 커지면 실패하거나 느려짐.  
4. **스트림 CPU** — 카탈로그 전 순회는 n=10³에서 가벼움. 매 프레임이 아니라 2.4 m 이동마다.  
5. **UV/시트** — 프롭은 시트 아님. 한 PNG = 한 쿼드. 캐릭터 스프라이트 시트와 예산이 다름.  
6. **칸 경계** — 프롭이 칸 로컬이라, 밀도를 올려도 **인접 칸 숲이 안 비침**. 시각 밀도 한계이지 GPU 한계는 아님.

**구조가 할 수 있는 것 / 없는 것** (데이터 빈약함과 분리)

| | |
|---|---|
| **할 수 있음** | CSV SSoT + % 좌표 + 스티커 빌보드 + (해안에서 검증된) InstancedMesh + 거리 스트림. **반복 나무 N×10²–10³/칸**은 이 구조의 연장선. GLTF가 전제 아님. |
| **지금 코드 그대로는 약함** | 인스턴싱이 `sea_wall` 하드코드. 내륙을 같은 CSV로 채우면 **개별 Mesh 경로**로 떨어짐. |
| **구조적 막다른 길 아님** | 포맷·렌더러 종류(2.5D 빌보드)가 RPG식 *반복* 식생을 금지하지 않음. 막히는 지점은 “행이 없다”가 아니라 “비-wall Mesh × 알파 필레이트 × 원반 n”. |
| **이 구조가 안 하는 것** | 연속 1 km 오픈월드 메시, 프롭 LOD, 텍스처 아틀라스, 마스크→자동 스캐터, 이웃 칸 프롭 스트리밍. |

**현재 데이터는 희소하다.** 아키텍처 헤드룸과 별개로, 들판/숲/i11에는 라이브 나무가 없다.

**불확실:** “모바일에서 Mesh 몇 장이 60fps인가”는 미실측. 데스크톱 WebGL은 보통 이 차수의 쿼드에 관대하고, 저가 모바일은 오버드로우에 민감.

### F-5. 1 km 시나리오 (차수)

전제: 유저가 말하는 맵 전체 ≈ 1 km = **설계 3×3 한 변**. 보행은 그 안의 십자 5칸. 3D는 칸마다 110 m로 축소해 보여 준다.

**같은 % 밀도라도 자가 두 개**

| 밀도 가정 | 110 m 칸 (실제 3D) 그루 수 | 스트림 원(~3630 m²) 안 | 설계 333 m 칸이라면 |
|---|---:|---:|---:|
| 지금 해안 띠 (~80/칸, 둘레) | ~80–93 | 해안 근접 시 수십 | 같은 %면 간격만 넓어짐 |
| 성긴 수목 0.01/m² | ~120 | ~36 | ~1 100 |
| 숲 패치 0.04/m² | ~480 | ~145 | ~4 400 |
| 빽빽 0.10/m² | ~1 200 | ~360 | ~11 000 |

5칸을 설계 면적으로 채우면 위 ×5. 3D에서는 **한 칸만 프롭 카탈로그에 있으므로** GPU가 보는 상한은 대체로 **스트림 원 + 해안 인스턴스 live**다. 1 km를 한 번에 그리지 않는다.

**인스턴스 vs 고유 텍스처 (차수)**

- **고유 PNG 2–8장** (지금 해안 2, 로스터 나무·풀·꽃 ~10): GPU ~수–십수 MB @512. InstancedMesh로 스트림 원 안 **10² 차수**는 해안 361행이 이미 같은 기법을 씀.  
- **고유 PNG 수십 장:** VRAM·바인드가 인스턴스 개수보다 먼저 증가.  
- **고유 PNG ≈ 인스턴스 수** (그루마다 다른 파일): 캐시가 돕지 못함. 이 구조의 전제가 아님.  
- 하늘 4096 세트(~10⁻¹ GB 차수)가 스티커보다 클 수 있음.

**플레이어가 1 km를 “설계 미터로” 건넌다** = 칸 3개 정도를 이어 입장 (3D 보행 ~330 m). 밀도 부하는 **칸 입장마다 리셋**되고, 누적 1 km 메쉬가 아니다.

**불확실:** “RPG 같다”의 목표 그루/m²는 코드에 없음. 위 표는 용량 스케일용이지 목표치가 아님.
