## 0. 문제 정의 (왜 이 기획서가 필요한가)

### 0-1. 사실 확인

- `HANDOFF.md`·`docs/gdd/00_INDEX.md`가 자체적으로 명시: **"원작: Capybara Go (영상 RE + 지시 사항)"** — XOOX는 애초에 카피바라고를 리버스엔지니어링한 프로토타입에서 출발했다.
- 2026-08-01 실측(직접 플레이) 결과, 현재 메인 화면 구조:
  - 상단: 요일 타임라인(점선 위 원형 마커, 전투/정예/보스 라벨) + 스탯바(LV·HP·ATK·DEF·GOLD)
  - 하단: 전체 폭 카드 로그 피드(내레이션·코멘터리·전투 로그가 한 피드에 순차 누적)
  - 최하단: 대박/중박 게이지 도크 + 스킬 선택 버튼
  - 이 구조는 **카피바라고 UI를 표면적으로 거의 그대로 리스킨한 수준**으로 판단됨(2026-08-02 세션에서 지시자도 동일 진단: "정작 실제 플레이하는 메인 화면은... 리스킨한 수준")
- 세계관·캐릭터(XOOX Rainbow Island, Tigon/Piper/Nashui/Olmas, 구조 조우 메카닉)는 이미 카피바라고 원형에서 상당히 멀어진 상태이나, **화면을 열었을 때의 첫인상(UI 크롬)만 원작과 흡사**하다는 게 핵심 문제.

## 3. 채팅(로그) UI 리뉴얼 【1순위】

### 3-1. 현재 상태 (실측)

전체 화면 폭을 쓰는 카드 피드 하나에 시나리오·코멘터리·전투 로그가 전부 순차 누적된다. 이 부분이 카피바라고 UI와 가장 흡사한 지점으로 판단됨(§0-1).

### 3-2. 변경안

- 로그를 **화면 오른쪽의 좁은 사이드 패널**로 이동
- 말풍선 형태로 렌더링해 **실제 채팅방처럼** 보이게 함(코멘터리의 "— 캐릭터명" 화자 표시와 자연스럽게 결합 가능)
- 화면의 나머지(왼쪽/메인)는 §4의 탐방 뷰가 차지

### 3-3. 스코프 판단

- 신규 데이터·신규 시스템 불필요. CSS 레이아웃 + 기존 카드 렌더링 함수의 출력 위치만 변경
- **최저 비용 / 최고 체감 효과** — 첫 착수 대상으로 확정

## 4. 탐방 뷰 신설 【2순위】

### 4-1. 기술 방향 (중요 — 2026-08-04 세션에서 정정됨)

이 문서 작성 직전 대화에서 기술 방향이 한 번 바뀌었다. 그 경위를 그대로 남긴다:

1. 최초 제안: 2026-08-01 이식해둔 배경 툴(`RegionBackdrop.ts`, Three.js 기반 FAR/NEAR/OBJ **패럴랙스 스크롤**)을 재활용하자고 제안함
2. 지시자가 Cozy Grove 스크린샷·영상을 제시하며 "이 이동 방식이 좋다"고 확인 — 확인해보니 Cozy Grove는 **좌우 스크롤이 아니라, 고정 카메라의 정적 장면 안에서 탭한 지점으로 캐릭터가 걸어가는 방식**
3. **정정:** 패럴랙스 스크롤과 탭투무브 탐방은 서로 다른 기술 패러다임 — `RegionBackdrop.ts`는 안 맞음. **정적 배경 이미지 + 탭 좌표로 캐릭터 이동(CSS transition)** 방식으로 확정

### 4-2. 왜 이 방향이 나은가

| 이유 | 설명 |
|---|---|
| 톤 일치 | Cozy Grove·Coffee Talk·Season·Alba 전부 "코지 게임" — 이 이동 방식이 그 정서와 정확히 맞음 |
| 스택 일치 | XOOX는 순수 DOM/CSS 기반(`main.ts`+`style.css`). Three.js 없이 CSS transition만으로 구현 가능 — **이식해둔 Three.js 배경 툴보다 오히려 구현이 단순함** |
| 카피바라고와의 차별화 | 카피바라고의 실제 코어 메카닉이 "전진하는 엔드리스 러너"이므로(BlueStacks 공략 확인), 좌우 스크롤 방식을 쓰면 오히려 원작에 더 가까워지는 역효과 위험이 있었음(2026-08-02 세션에서 레이싱 아이디어 검토 중 발견) — 탭투무브는 이 위험을 완전히 회피함 |

### 4-3. 진행도 시각화

Cozy Grove의 "도와주면 지역이 흑백→컬러로 번져나간다" 연출을 **23번 문서(무지개섬 파견)의 시각적 표현**으로 재활용 제안 — 별도 신규 기획이 아니라 기존 23번 문서 실행 시의 연출 방식으로 편입.

### 4-4. 필요 리소스 (공백 확인)

- 장면별 배경 아트: 이식된 몬카피바라 샘플(`region_ws_01~06`)은 각도·톤이 다르므로 그대로 못 씀 — **별도 제작 필요**(cyber-breeds 파이프라인으로 제작 가능하나 실제 산출물은 아직 없음)
- 캐릭터 이동 스프라이트: 현재 breed_01(메카독) 등은 로비 정면 샷만 확정, 인게임 측면 idle 기준 포즈까지만 있고 이동 프레임은 미제작(`docs/cyber-breeds/05_game_ingame_sprite/breed_01/` 상태 참고)
- 탭 가능 지점(이벤트/펫 위치) 정의 방식 — 미확정

## 7. 롤아웃 순서 (요약)

```
① 채팅 → 오른쪽 소형 패널              [CSS/레이아웃만, 최저비용·최고효과]
        ↓
② 탐방 뷰(정적 배경 + 탭투무브)         [신규 렌더링 로직 소규모, 아트 리소스 공백 있음]
        ↓
③ 스크랩북(Tigon 기억조각 열람 UI)      [22번 문서 데이터 위에 화면 1개만 추가]
        ↓
④ 폰 UI(도감·구조일지·펫상태 분리)      [기존 화면 재구조화, 스코프 최대]
```

각 단계는 독립적으로 출시 가능하도록 설계 — 어느 단계에서 멈춰도 그 자체로 완결된 개선이 되게 한다.

## 8. 바뀌지 않는 것 (명시적 확인)

지시자 원칙 1(§0-2)에 따라 아래는 **이 리뉴얼로 전혀 손대지 않는다**:

- `engine.ts`의 요일(day) 기반 진행 로직 전체
- 대사 → 선택 → 전투로 이어지는 흐름 자체
- 구조 조우(5턴 2지선다 태그매칭) 메카닉
- 등급 6단계·미니게임 게이지 시스템의 **내부 로직**(외형 표현만 §6에서 바뀔 수 있음)
- 22·23·24번 문서에 이미 정리된 컨텐츠의 **데이터/로직 설계** 자체(이 문서는 그 UI 표현 방식만 구체화함)

## 9. 리스크 및 결정 필요 사항

| # | 항목 | 내용 |
|---|------|------|
| 1 | **코드 구조 리스크** | `main.ts`(155KB)·`style.css`(114KB)가 단일 파일 — 여러 단계를 동시에 건드리면 회귀 원인 추적이 어려움. §7 순서를 반드시 순차로 지킬 것 |
| 2 | **미커밋 변경 누적** | 이전 리뷰에서 지적된 대로 마지막 커밋 이후 대량의 미커밋 변경이 쌓여 있음 — 이 리뉴얼 착수 전 커밋 체크포인트 권장 |
| 3 | **아트 리소스 공백** | 탐방뷰 배경·캐릭터 이동 스프라이트가 전무. 이식된 스프라이트 툴(§4-4)은 파이프라인만 있고 산출물 없음 — 실제 그림 작업이 병행돼야 진행 가능 |
| 4 | **폰 UI 스코프** | §6은 기존 여러 화면을 재구조화해야 해서 가장 큰 작업 — 1~3순위 완료 후 재검토 필요할 수 있음 |
| 5 | **탭 가능 지점 설계 미확정** | §4-4, 탐방 장면 안에서 "여기 이벤트가 있다"를 어떻게 표시할지(항상 보이는 아이콘 vs 접근 시 등장 등) 결정 필요 |
