# 27. 지역 이동 구조 (RPG식 A→B→A) — 유연 설계

> 작성: 2026-08-04 · 상태: 【아키텍처만 확정 · 실제 지역/NPC 콘텐츠는 미정 · 지시자 명시: "나중에 수정 가능한 구조로"】
> 전제 문서: [`25_UI연출_리뉴얼_기획서.md`](./25_UI연출_리뉴얼_기획서.md) §4(탐방 뷰) · [`26_UI_와이어프레임.md`](./26_UI_와이어프레임.md) §3

## 0. 지시자 요청 요약

- 이동을 **RPG처럼** 하고 싶음 — A지역에서 NPC를 만나고, B지역에 갔다가, 다시 A지역으로 돌아오는 개념
- **아직 구체 기획(어떤 지역이 있고 어떻게 연결되는지)은 확정 안 됨**
- 그러니 **나중에 지역·연결을 자유롭게 바꿔도 되는 구조**로 지금 설계해야 함
- Cozy Grove의 화면 구성/컨셉을 잘 이해해서 참고할 것 — 단, **가로 모드가 필요하다고 판단되면 재검토**

## 1. Cozy Grove 재조사 결과 — 중요한 차이 하나

| 항목 | Cozy Grove 실제 구조 | 지시자가 말한 "RPG식" 구조 |
|---|---|---|
| 화면 방향 | 세로(포트레이트), 탑다운/아이소메트릭 | (미정 — 세로 유지 가능성 높음) |
| 공간 구조 | **섬 하나가 계속 넓어지는 단일 연속 공간**(완전 개방 시 안전구역 6곳) | **개별 지역(맵)들이 서로 연결된 그래프**(마을A↔필드↔마을B) |
| 연결 방식 | 안전구역 배치·연결이 **매일 랜덤하게 바뀜**(절차적) | 지역 간 연결이 **고정**되어 있고, 왕복 가능 |

→ **결론: 두 구조가 미묘하게 다르다.** Cozy Grove는 "한 공간이 점점 넓어지는" 쪽이고, 지시자가 원하는 건 "여러 개의 고정된 지역을 오가는" 고전 RPG 쪽에 가깝다. 그래서 Cozy Grove의 화면 구성(세로, 탑다운, 탭투무브, 진행도 시각화)은 그대로 참고하되, **공간 구조 자체는 Cozy Grove를 그대로 베끼지 않고 "지역 그래프" 방식으로 설계**한다.

## 2. 설계 원칙 — 콘텐츠와 구조의 분리

지시자 요청의 핵심은 "나중에 수정 가능해야 한다"는 것. 그래서 **지역·연결·NPC를 전부 데이터(CSV)로 빼고, 코드는 그 데이터를 그리는 방법만 안다**는 원칙으로 설계한다 — XOOX 프로젝트의 기존 철학("수치·문구·구성 = CSV SSoT, 코드는 규칙 엔진만")과 동일한 방향.

### 2-1. 데이터 구조 (신규 CSV, 잠정)

> **네이밍 주의(2026-08-04 발견):** `location_config.csv`라는 이름은 **이미 사용 중**이다 — 기존 분기 이벤트 지역 시스템(`entry_path`/`linked_minigame_id`/`offer_leave` 등, 예: `loc_mercenary`, `loc_pirate`)이 이 이름을 쓰고 있고, 이 문서가 말하는 "탐방용 지역 그래프"와는 완전히 다른 스키마다. 그래서 아래는 **`area_*` 접두어**로 명명해 충돌을 피한다.

> **구현 완료(2026-08-04).** 아래는 실제 구현된 스키마다. 초안 대비 **배경 아트가 없어 플레이스홀더 색 컬럼이 추가**됐고, `exit_point`는 모호했던 자유서술 대신 **`LEFT`/`RIGHT` 열거값**으로 확정했다.

```
area_config.csv                    ← "지역"(탐방용) 자체
  area_id            PK (예: area_sewer_gate)
  display_name       표시 이름 (화면 좌상단 이름표)
  sky_top/sky_bottom  배경 그라디언트 색 ← 아트 없을 때의 플레이스홀더
  ground_color        땅 색
  ground_h_pct        화면 아래에서 땅이 차지하는 비율(%)
  background_asset    배경 이미지 경로 — 채워지면 위 색보다 우선
  stage_map_id        어느 스테이지(기존 stage_map_config)에 속하는지
  note

area_connection_config.csv         ← 지역 간 "길"
  connection_id      PK
  from_area_id        출발 지역
  to_area_id          도착 지역
  exit_point          LEFT | RIGHT  ← 화면의 어느 가장자리로 나가는지
  bidirectional        TRUE면 반대 방향 통로가 자동 생성(반대편 가장자리로)
  unlock_condition     조건부 개방 — **미구현**(값이 있으면 그 통로를 건너뜀)

area_npc_config.csv                ← 지역 안 상호작용 지점
  npc_id             PK
  area_id             어느 지역에 있는지
  x_pct               지역 가로폭 기준 위치(%)
  icon / label        화면에 표시할 아이콘·이름
  trigger_type        MEMO(구현) / RESCUE·EVENT 등(미구현, 확장 예정)
  trigger_ref         기존 rescue_animal_config 등의 id 참조(확장용)
  appear_condition     ALWAYS만 구현
  flavor_text         MEMO일 때 채팅에 남길 문구
```

**기존 `location_config.csv`와의 관계:** 그 시스템은 "분기 이벤트가 발생하는 지점"(임시 이름의 나열)이고, 이 `area_*`는 "플레이어가 탐방 뷰에서 실제로 걸어다니는 공간"이다. 서로 다른 축이라 지금은 독립적으로 두되, 나중에 특정 `area`가 특정 `location`(분기 이벤트)을 포함하도록 연결할 여지는 남겨둔다(예: `area_npc_config.trigger_type=BRANCH_EVENT`, `trigger_ref=loc_mercenary`).

### 2-2. 왜 이렇게 나누는가

- **지역 추가/삭제/재배치**를 코드 수정 없이 CSV 행 추가/삭제/수정만으로 가능하게 함 — 지시자가 "아직 기획 확정 안 됐다"고 한 것에 대한 직접적 대응
- `location_connection_config`가 그래프의 "간선(edge)" 역할 — A↔B, B↔C처럼 자유롭게 확장 가능. **A→B→A 왕복**은 `bidirectional=TRUE` 한 줄이면 끝
- `location_npc_config`는 새 시스템이 아니라 **기존 rescue/day_event/minigame_entry 시스템을 지역이라는 "장소"에 배치만 하는 라우팅 테이블** — 25번 문서 원칙("새 시스템보다 기존 데이터 재활용")과 일치

### 2-3. 화면에서는 이렇게 보인다 (26번 문서 §3 확장)

```
┌───────────────────────────┐
│  [지역: 하수도 지구 입구]        │
│                           │
│     🌳       🌳            │
│         🚶                │
│              🐾(NPC/이벤트)     │
│                           │
│  ◀ 이전 지역으로            │  ← location_connection의
│                    다음 지역 ▶│    exit_point 시각화
└───────────────────────────┘
```

- 화면 가장자리(또는 특정 오브젝트)를 탭 → `area_connection_config`에서 매칭되는 행 찾음 → 다음 `area_id`의 배경으로 전환
- 되돌아가는 것도 같은 방식(같은 connection이 `bidirectional=TRUE`면 반대 방향도 자동)

## 3. 화면 방향(세로/가로) 판단 — 【가로 확정 2026-08-04】

> **결론이 바뀌었다.** 아래 초안은 "세로 잠정 + 필요시 재검토"였으나, 실제 구현·실측 과정에서 재검토 트리거가 발동해 **가로로 확정**됐다. 경위를 남긴다.

### 3-1. 초안 (2026-08-04 오전)

- 기본값 세로. 이유: (1) Cozy Grove도 세로 (2) XOOX 기존 화면이 전부 세로 기준이라 전환 비용 큼 (3) 가로가 필요하다는 구체적 근거가 아직 없음
- **재검토 트리거(지시자 명시):** "가로 모드가 필요하다고 판단되면 다시 판단을 하던가"

### 3-2. 트리거 발동 — 실측 근거

25번 문서 §3(채팅 사이드 패널)을 실제로 구현해 세로 420px 프레임에서 측정한 결과:

| 프레임 폭 | 채팅 패널 폭 | 카드 텍스트 영역 | **한 줄 글자수** | 판정 |
|---|---|---|---|---|
| 420 (세로) | 147 | 103 | **7~8자** | 판독 불가 |
| 812 (가로) | 284 | 240 | **20자** | 카톡 수준 |
| 844 (가로) | 295 | 251 | 21자 | 양호 |
| 1000 (채택) | 350 | 314 | **26자** | 여유 |

127자짜리 나레이션 한 장이 세로에서 **11줄**로 쪼개졌다. 사이드 패널 방식 자체가 세로 420px에서는 성립하지 않는다.

### 3-3. 왜 Cozy Grove는 세로인데 우리는 안 되나 (중요)

Cozy Grove는 세로가 맞지만 **상시 노출되는 사이드 채팅 패널이 없다** — 대화는 전체화면 오버레이로 띄운다. 지시자가 종합한 방향("거의 전체화면 탐방 + 오른쪽에 작게 채팅방처럼")은 Cozy Grove의 탐방 화면과 **별도 출처(Coffee Talk/메신저형 UI)의 사이드 패널**을 합친 것이고, 이 조합은 구조적으로 가로(또는 태블릿) 폭을 전제한다. 레퍼런스를 합칠 때 각자의 화면 전제까지 함께 따라오지 않는다는 사례로 기록해 둔다.

### 3-4. 확정 사항

- **화면 방향 = 가로.** 프레임: `width: min(100vw, 1000px)` × `height: min(100vh, 480px)`
- 이 문서의 데이터 구조(`area_*` CSV 3종)는 **방향과 무관** — 배경 이미지 비율과 CSS만 영향받으므로 재설계 불필요(초안의 이 판단은 그대로 유효했음)
- 구현·검증 결과: [`28_개발_실행계획.md`](./28_개발_실행계획.md) §7

## 4. 구현 현황 (2026-08-04)

### 4-1. 완료

- **CSV 3종 + 로더**(`data.ts`) · 타입(`types.ts`) · 렌더/이동 모듈 **`src/explore.ts`**(신설 — `main.ts` 비대화 회피)
- 시드 데이터 3지역: 하수도 입구 ↔ 하수도 본관 ↔ 폐자재 야적장 (양방향), 이벤트 지점 6개
- **움직임 세트**(전부 CSS, rAF 금지 규칙 준수):
  | 동작 | 구현 |
  |---|---|
  | 대기 | 호흡(`actor-breathe`) + 그림자 연동 |
  | 걷기 | 탭 지점으로 이동, **거리에 비례한 소요시간**(165px/s, 0.26~1.5s) + 통통 튀는 bob·기울기 |
  | 방향 전환 | `scaleX` 반전 + 짧은 스쿼시(`actor-turn`) |
  | 도착 | 눌렸다 펴지는 스쿼시(`actor-land`) |
  | 지역 이동 | 가장자리로 걸어나감 → 페이드 → 반대편에서 진입 → 안쪽으로 몇 걸음 |
  | 이벤트 접근 | 지점 옆까지 걸어가 멈춤 → 제자리 홉(`actor-react`) → 채팅에 플레이버 출력 |
  | 이벤트 지점 | 상시 맥동(`poi-pulse`), 발견 시 강조(`poi-found`) |
  | 지역 이름표 | 진입 시 슬라이드 인 후 흐려짐 |
- **게임 상태 연동**: `EXPLORE_MODES`(IDLE·EVENT·LOCATION_*)에서만 노출, 전투/구조/스킬선택 진입 시 자동 숨김
- 콘솔 훅 `__explore()` 로 수동 토글

### 4-2. 검증 (실플레이)

지역 3곳 순회 + **A→B→다시 A 왕복** 확인 · 탭 이동/방향전환/도착 모션 동작 확인 · 이벤트 지점 탭 → 채팅 카드 출력 확인 · 스킬선택 모드 전환 시 탐방 자동 숨김 확인 · 넘침 0건 · `tsc --noEmit` + 빌드 통과.

### 4-3. 미구현 (다음 차례)

| 항목 | 메모 |
|---|---|
| 실제 배경 아트 | 지금은 CSV 색 플레이스홀더. `background_asset` 채우면 즉시 교체됨 |
| 캐릭터 스프라이트 | 지금은 CSS 도형. breed_01 이동 프레임 제작 후 교체 |
| `trigger_type` 확장 | MEMO만 구현. RESCUE/EVENT를 기존 시스템에 연결하는 배선 필요 |
| `unlock_condition` | 조건부 통로 — 값이 있으면 현재는 통로 자체를 숨김 |
| 지역과 일차(day) 진행의 관계 | **미정** — 지역 이동이 하루를 소모하는지, 하루 안에서 자유 이동인지 |
| 세로 방향 대응 | 가로 확정(§3)이라 당분간 불필요 |
